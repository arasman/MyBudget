# Exploration: password-management

**Date**: 2026-07-13
**Change**: password-management
**Status**: Complete — ready for proposal

---

## Summary

The `password-management` change has a solid auth foundation to build on. `ISecurityAuditWriter`, `IEmailSender`, the `Invitation` BCrypt-token pattern, and all security audit infrastructure are production-ready. The main work is 4 new `User` columns, a new `PasswordResetToken` entity, 3 new VSA slices (RequestPasswordReset, ResetPassword, ChangePassword), lockout/forced-change enforcement inside `LoginUserHandler`, and 3 new frontend views/components.

---

## Current State

### Backend auth infrastructure

`User` entity has `PasswordHash`, `LastLoginAt`, but **no** `FailedLoginAttempts`, `LockoutUntil`, `PasswordChangedAt`, or `ForcePasswordChange`. All four must be added.

`LoginUserHandler` uses Dapper for credential lookup, then BCrypt.Verify, then EF to update `LastLoginAt`. It already injects `ISecurityAuditWriter` and writes `FailedLogin` and `SuccessfulLogin` events. The lockout enforcement and `ForcePasswordChange` check must be inserted at the top of `Handle`, before BCrypt.Verify.

`ISecurityAuditWriter` / `SecurityAuditWriter` are fully operational at `SharedKernel/Services/`. The `PasswordChanged` event is reserved per the audit-log spec. `AccountLocked` is also required. Both are written via `_auditWriter.WriteAsync(eventName, ...)` — same pattern already used in LoginUser, RegisterUser, LogoutUser, and AcceptInvitation handlers.

### Token pattern (for reset links)

The `Invitation` entity stores `TokenHash` (BCrypt, workFactor 6), `ExpiresAt`, `UsedAt`. The raw token is generated by `JwtTokenService.GenerateRefreshToken()` (64-byte random Base64Url). This entire pattern is reusable verbatim for password-reset tokens. A new `PasswordResetToken` entity modeled after `Invitation` (without BudgetId/Role/InviteeEmail) is the correct approach.

### Email infrastructure

`IEmailSender` → `EmailChannel` → `EmailBackgroundService` (MailKit) is live. Config keys: `Email:SmtpHost`, `Email:SmtpPort`, `Email:FromName`, `Email:FromAddress`. Mailpit is in Docker Compose on ports 1025/8025. No new email infrastructure is needed — the handler writes an `EmailMessage` to the channel and returns immediately.

### Policy configuration

The `AuditLog:RetentionDays` / `IAuditRetentionPolicy` / `AppSettingsAuditRetentionPolicy` pattern is the established way to expose configurable thresholds. A new `IPasswordPolicyService` backed by a `PasswordPolicy` appsettings section follows the same pattern exactly.

### Frontend

`auth.store.ts` has login/register/logout/refresh/fetchMe. No password-reset or change-password methods exist. The Axios 401 interceptor retries once silently and is not affected by password-management flows. The router has `/login`, `/register`, `/invitations/accept` as public routes. Two new public routes needed: `/forgot-password`, `/reset-password`. AppLayout user dropdown contains only a Logout button — a "Change Password" entry must be added. `en.json` has `auth.login.*` and `auth.register.*` — new `auth.password.*` namespace needed.

## Approaches Considered

| Approach | Pros | Cons | Effort |
|----------|------|------|--------|
| **A — Standalone `PasswordResetToken` table (mirrors `Invitation`)** | Exact pattern match, clean rollback, separate semantics, easy to query | One additional table | Medium |
| B — Reuse `RefreshTokens` with a `Purpose` discriminator | No new table | Mixed semantics, alters existing busy table, violates SRP | Medium (higher maintenance) |
| C — Stateless signed JWT for reset tokens | No DB write on issuance | Cannot invalidate mid-flight, inconsistent with invitation pattern | Low–Medium |

**Recommendation: Approach A** — mirrors `Invitation` pattern exactly. Consistent, low-risk, independently revocable.

## Risks

| ID | Severity | Description |
|----|----------|-------------|
| R-001 | Medium | Lockout check MUST run before BCrypt.Verify — early-exit avoids timing inconsistency and prevents BCrypt delay on already-locked accounts |
| R-002 | Low | `RequestPasswordReset` MUST return 200 even when email is unknown (anti-enumeration) |
| R-003 | Low | `ForcePasswordChange` must be cleared in the same `SaveChangesAsync` as new `PasswordHash` in both ResetPassword and ChangePassword |
| R-004 | Low | `PasswordChangedAt` nullable — `null` means never changed; forced-change interval check must fall back to `CreatedAt` as baseline |
| R-005 | Low | Migration alters `Users` table (additive columns only); nullable + DEFAULT columns are safe in Postgres with existing data |

## Scope Boundaries Confirmed

**In scope**:
- Password recovery by email (token link, Mailpit in dev)
- Change password from User Account Settings
- Forced-change policy (configurable interval; detected at login, blocks session until changed)
- Account lockout after N failed login attempts
- `PasswordChanged` + `AccountLocked` SecurityAuditLog events

**Out of scope**:
- OAuth, SSO, MFA (MVP B)
- Admin-forced reset, password history, admin unlock dashboard
